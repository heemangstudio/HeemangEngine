# hwp5-container: HWP 5 container, records and binary data

This unit covers everything a reader does before DocInfo and BodyText semantics: deciding what kind of file it was given, opening the HWP 5 compound file, reading the FileHeader, undoing compression and distribution encryption, framing records, enforcing resource budgets, locating and loading BinData (including embedded OLE storages), and the document-wide passes that run once all sections are parsed (auto-number assignment, origin-variant fixups, linked-image paths).

## Connections

| Direction | Peer unit | Contract |
| --- | --- | --- |
| In | caller (app, CLI, hub) | Raw bytes plus an acquisition policy (untrusted, approved local file, regenerated by our own serializer). See [limits.md](limits.md). |
| Out | HWPX package reader | Inputs whose first 4 bytes are the ZIP local-file signature. The HWPX reader owns everything after detection. |
| Out | HWP 3.0 reader | Inputs starting with the 17-byte HWP 3 signature. The HWP 3 reader also calls the auto-number pass of this unit. |
| Out | HWPML (HML) reader | Inputs whose XML root is `HWPML` with a non-empty `Version`. |
| Out | DocInfo / BodyText unit | Decompressed (and, for distribution documents, decrypted) record streams, framed into records. That unit owns record payload semantics. |
| Out | media, OLE, chart and equation units | BinData payloads by DocInfo ordinal, OLE storage contents (presentation metafile, OOXML chart, legacy chart `Contents`, equation script, native image). |
| Out | layout and pagination | Provenance flags (HWP 3 lineage, HWPX lineage) and the variant corrections of [post-parse.md](post-parse.md). |
| Out | HWP 5 writer | Raw FileHeader bytes, raw DocInfo and section streams, every unmodelled CFB stream (with its path), BinData source encoding (compressed or not, OLE prefix), and the stored auto-number values. |

## Processing order (HWP 5)

1. Check the raw input size against the acquisition policy, then against the container budget.
2. Detect the format ([format-detection.md](format-detection.md)).
3. Open the CFB container. Validate the header, FAT, DIFAT and directory before building anything proportional to declared counts ([cfb.md](cfb.md)).
4. Read `FileHeader`, check the signature, read version and flags ([file-header.md](file-header.md)). A password-encrypted document stops here.
5. Read `DocInfo`; inflate it when the document is compressed ([compression.md](compression.md)); frame records ([records.md](records.md)) and hand them to the DocInfo parser.
6. For each section index from 0 while a section stream exists: read `BodyText/SectionN` (or `ViewText/SectionN` for distribution documents, decrypted per [distribution.md](distribution.md)), inflate, frame, hand to the BodyText parser.
7. Read the preview image and preview text.
8. Collect every remaining stream for round trip.
9. Register BinData items for lazy loading ([bindata.md](bindata.md)).
10. Run the document passes in this order ([post-parse.md](post-parse.md)): auto numbers, HWP 3 margin correction, HWP 3 lineage identification with spacing correction, linked-image paths, line-position normalization for HWP 3 lineage, then the private hyperlink-format stream.

## Ground truth used

- Hancom-saved fixtures (stored line segments, stored auto numbers, stored deflate trailers, distribution headers), probed directly from the bytes.
- Hancom page-count pins (Hancom 2020/2022, Mac and Windows) for HWP 3 lineage documents.
- Old-engine behavior, labeled as such, where no Hancom evidence exists.

## Main findings for builders

- Hancom writes an 8-byte trailer after every raw-deflate stream: CRC-32 of the inflated bytes, then the inflated length. Files from other writers omit it. Readers ignore it; writers that want byte-identical Hancom output must emit it ([compression.md](compression.md)).
- BinData items must be addressed by their DocInfo ordinal (1-based) and never by position in a list of successfully loaded items. The old engine's positional list shifts every later picture when an earlier item is a link or a missing stream ([bindata.md](bindata.md)).
- Footnote and endnote numbers belong to the note controls, not to the auto-number controls inside them. Hancom counts notes whose body has no number control ([post-parse.md](post-parse.md)).
- The old HWP 3 lineage spacing halving contradicts the line positions Hancom stores in the same files. Do not port it without a parity check ([post-parse.md](post-parse.md)).
- A distribution document's AES key is the UTF-16LE encoding of the first 8 hex digits of a SHA-1 hex string; the option flags follow the 80-byte hash ([distribution.md](distribution.md)).

## Open questions

- How Hancom numbers figures when the stored numbers skip values with no visible cause (`tac-img-02.hwp`, see [post-parse.md](post-parse.md)).
- Whether the 1600 HU bottom tolerance is specific to HWP 3 lineage files or a general Hancom fit rule (measurements in [post-parse.md](post-parse.md)).
- The password (bit 1) encryption algorithms. No fixture exists and the public documents do not describe them ([distribution.md](distribution.md)).
- Whether Hancom accepts a raw-deflate stream without the CRC-32 trailer in every version. Files saved by the old app lack it and reopen in Hancom for Mac; Windows was not checked.
